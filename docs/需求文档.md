## 1. 项目概述

### 1.1 项目定位一句话

> 把 GitHub 上热门高星的开源工具**下载到本地本项目内**，由本项目作为统一宿主进行封装管理，用户在一个窗口里选中某个工具，该工具即在窗口内启动运行、直接使用——**一个窗口装下所有工具**。

### 1.2 与"工具导航站"的本质区别

| 对比项 | 工具导航站（v1 方案） | 本项目（v2 方案） |
| --- | --- | --- |
| 工具在哪里 | 在 GitHub / 在线服务上，本地只有链接 | **工具代码/产物真实存放在本项目目录内** |
| 使用方式 | 跳转浏览器，或引导用户自行部署 | 宿主负责下载、装依赖、起服务，**窗口内直接打开使用** |
| 离线可用 | 否（依赖对方在线服务） | **是**（下载安装完成后完全本地运行） |
| 管理责任 | 无 | 宿主统一管理工具的安装、启动、停止、更新、删除 |

### 1.3 产品目标

1. **收录**：持续搜集 GitHub 上各行业、各用途的热门高星**可运行工具项目**（Web 应用、静态工具、CLI、Docker 服务、桌面程序）；
2. **下载**：一键把选中的工具下载到本项目管理的工具目录中（git 克隆或 Release 下载，浅克隆节省空间）；
3. **封装**：本项目作为宿主为每个工具提供统一的"适配层"（启动配方），屏蔽各工具安装/启动方式差异；
4. **使用**：在宿主唯一窗口内，点击工具即完成启动并在窗口内打开使用界面，全程不离开本窗口、不打开浏览器；
5. **管理**：统一管理所有已装工具的运行状态、版本更新、磁盘占用与删除。

### 1.4 核心用户价值

| 价值 | 说明 |
| --- | --- |
| 开箱即用 | 用户不需要懂 git、npm、python、docker，宿主自动完成下载安装启动 |
| 窗口内使用 | 所有工具在同一个窗口里打开使用，体验如同"内置功能" |
| 完全离线 | 工具下载到本地后，断网也能继续使用 |
| 统一管理 | 启动/停止/更新/卸载全部在宿主内完成，进程、端口、磁盘一目了然 |
| 干净不污染系统 | 工具全部限制在本项目目录内，删除工具即彻底清除 |

### 1.5 名词定义

| 名词 | 定义 |
| --- | --- |
| 宿主（Host） | 本项目构建出的桌面应用，即那个"聚合窗口"，负责管理并在窗口内打开所有工具 |
| 工具仓（Toolyard） | 本项目内存放已下载工具的目录（开发态为仓库内 `tools/`，安装态为应用数据目录下 `tools/`） |
| 工具清单（Manifest） | 描述某个工具"从哪下载、怎么安装、怎么启动、怎么打开"的配置文件，是宿主封装工具的核心契约 |
| 工具目录（Catalog） | 可供下载的工具清单集合，数据来自 GitHub 高星项目采集 + 预置 Manifest 库 |
| 应用内打开 | 工具界面呈现在宿主窗口内（内嵌 WebView 或内嵌终端），而非弹出系统浏览器或独立窗口 |

## 2. 用户画像与使用场景

### 2.1 目标用户

| 画像 | 描述 | 核心诉求 |
| --- | --- | --- |
| 普通用户 | 不会配置开发环境，但想用 GitHub 上的优秀工具（图片压缩、格式转换、笔记、下载器…） | 一键下载、点开就用，零命令行 |
| 开发者 | 常用各类 CLI / 本地 Web 工具 | 一个入口管理所有本地工具，随手启停 |
| 折腾爱好者 | 喜欢自部署各种高星项目 | 免去逐个 clone、装依赖、记端口的麻烦 |

### 2.2 典型场景

**场景 1：下载并使用一个 Web 工具**
用户在"工具目录"里看中一个高星 Markdown 编辑器（类型徽标：Web 应用）→ 点击"获取" → 宿主克隆仓库到 `tools/markdown-editor/`、自动执行依赖安装 → 完成后卡片变为"已就绪" → 点击卡片 → 宿主启动本地服务并等待健康检查通过 → **宿主窗口内嵌页面打开该编辑器**，用户直接写作。关闭时宿主自动停止后台服务。

**场景 2：使用命令行工具**
用户获取一个高星 CLI 图片处理工具 → 已就绪后点击 → 宿主窗口内出现内嵌终端 → 用户直接输入命令，或使用宿主渲染的"参数表单" → 执行并查看输出。

**场景 3：离线使用**
用户提前下载了 5 个工具。出差断网后打开宿主，5 个工具全部可正常启动使用。

**场景 4：更新与清理**
宿主提示某工具有新版本 → 点击"更新" → 自动拉取新代码并重装依赖 → 继续使用。磁盘紧张时，在"存储管理"里看到各工具占用（含依赖体积），一键删除不再使用的工具。

**场景 5：自带工具入库**
用户手动输入一个 GitHub 仓库地址 → 宿主尝试自动识别其技术栈并生成适配 Manifest → 识别失败时引导用户选择运行类型并填写启动命令 → 入库到"我的工具"。

## 3. 产品形态与技术选型

### 3.1 形态决策：桌面应用（宿主壳）

只有桌面应用能同时满足：窗口内嵌 WebView 打开本地 Web 工具、内嵌终端运行 CLI、管理本地进程与文件、完全离线。

| 决策项 | 推荐方案 | 备选 | 理由 |
| --- | --- | --- | --- |
| 宿主框架 | **Electron** | Tauri | 绝大多数 GitHub 热门 Web 工具是 Node 技术栈，Electron 自带 Node 运行时，宿主可直接为工具执行 `npm install` / `npm start`，无需用户另装 Node；进程管理、PTY 终端生态成熟。代价是体积与内存较大，可接受 |
| 前端 UI | Vue 3 / React + 组件库 | — | 渲染宿主界面 |
| 工具页面承载 | Electron `<webview>` / BrowserView | — | 每个运行中的 Web 工具一个隔离视图 |
| 内嵌终端 | xterm.js + node-pty | — | 承载 CLI 工具与安装日志 |
| 本地数据 | SQLite（目录/收藏/状态）+ JSON Manifest 文件 | — | Manifest 是文件，便于版本管理与社区贡献 |
| 运行时管理 | 宿主内置 Node；Python/Docker 检测+引导安装 | 内置多运行时 | 内置 Node 覆盖最大公约数；其余按需 |
| 下载通道 | git clone --depth 1 / Release zip / codeload 归档，支持镜像加速 | — | 应对网络受限；浅克隆控空间 |

### 3.2 本项目仓库结构（开发态）

```
all-tools/
├─ host/                     # 宿主应用源码（Electron 主进程 + 渲染层）
│  ├─ main/                  # 进程管理、下载器、Runner、端口池
│  └─ renderer/              # 聚合窗口 UI
├─ manifests/                # 预置工具适配清单库（随主仓库版本管理，核心资产）
│  ├─ catalog.json           # 工具目录索引（含 GitHub 元数据快照）
│  └─ tools/<tool-id>.json   # 每个工具一份 Manifest
├─ tools/                    # 工具仓：已下载工具的落盘目录（gitignore，不入库）
│  └─ <tool-id>/
├─ runtimes/                 # 内置/托管的运行时（如内置 Node，gitignore）
├─ data/                     # SQLite、日志、端口分配记录（gitignore）
└─ docs/                     # 文档
```

> 双形态说明：开发态下 `tools/`、`runtimes/`、`data/` 直接落在本仓库内；安装态下它们落在系统应用数据目录（或用户自选目录），由统一路径解析器屏蔽差异，详见 FR-DIST-01/02。

### 3.3 总体架构

```
┌───────────────────────────────────────────────────────┐
│                    宿主主窗口（唯一窗口）                  │
│   工具目录 │ 我的工具 │ 收藏/最近 │ 设置                    │
│   ┌─────────────────────────────────────────────┐     │
│   │      工具使用视图（按工具切换）                    │     │
│   │   内嵌 WebView（Web 工具） / 内嵌终端（CLI）       │     │
│   └─────────────────────────────────────────────┘     │
├───────────────────────────────────────────────────────┤
│                   宿主核心服务（主进程）                   │
│  生命周期管理器 │ 进程守护 │ 端口池 │ 健康检查 │ 下载器      │
├───────────────────────────────────────────────────────┤
│                     工具适配层（Runner）                  │
│  web-node │ web-python │ web-static │ docker │ cli │ exe │
├───────────────────────────────────────────────────────┤
│              工具仓 tools/ ＋ Manifest 库 ＋ SQLite       │
├───────────────────────────────────────────────────────┤
│                目录数据采集（GitHub 高星/Trending）        │
└───────────────────────────────────────────────────────┘
```

## 4. 功能需求

> 优先级：**P0** = MVP 必须；**P1** = 第二迭代；**P2** = 远期。
> 编号：FR-模块-序号。

### 4.1 模块一：工具目录采集（决定"能下载什么"）

| 编号 | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| FR-CAT-01 | GitHub 高星采集 | P0 | 通过 GitHub Search API 按 `stars:>=阈值`（默认 1000，可调）+ 关键词（tool/app/utility 等）拉取候选；抓取名称、简介、star、语言、topics、license、主页、Release 信息 |
| FR-CAT-02 | Trending 采集 | P1 | 每日抓取 GitHub Trending，补充新晋热门工具 |
| FR-CAT-03 | 可运行性识别 | P0 | 判定候选仓库属于哪种运行类型：`web-node`（有 package.json 且含 start/dev 脚本）/ `web-python`（requirements.txt + Flask/FastAPI/Streamlit 等特征）/ `web-static`（含 index.html 的纯前端）/ `docker`（有 docker-compose.yml 或 Dockerfile）/ `cli` / `desktop`（提供安装包 Release）；无法判定归入"待适配" |
| FR-CAT-04 | 分类体系 | P0 | 预置一级分类：开发工具、AI 与大模型、图像与设计、音视频、文档与办公、下载与网络、安全与隐私、系统与硬件、数据与数据库、自动化效率、生活实用、其他；每工具一个主分类 + 多标签（免安装、需 Docker、需 Python、中文界面等） |
| FR-CAT-05 | 中文简介 | P1 | 英文简介自动翻译为中文（可配置翻译/LLM API，可关闭） |
| FR-CAT-06 | 目录同步 | P0 | 目录数据每日增量更新（star、版本、是否归档）；全部缓存至本地 SQLite，断网可浏览 |
| FR-CAT-07 | Token 与限速 | P0 | 支持配置 GitHub PAT 提升配额；请求限速与退避；支持镜像/代理配置 |
| FR-CAT-08 | 预置 Manifest 库 | P0 | 项目官方维护的已验证适配清单（M1 至少覆盖 10 个热门工具），保证这些工具"一键即用"；随宿主安装包内置，并支持运行时从官方源远程增量更新（FR-DIST-03），使老版本宿主也能获得新适配；社区可提交新 Manifest |

### 4.2 模块二：下载与入库（工具进入本项目）

| 编号 | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| FR-DL-01 | 一键获取 | P0 | 在目录中点击"获取"：宿主将工具下载到 `tools/<tool-id>/`；默认 `git clone --depth 1`，无 git 环境或纯发布产物时下载 Release/源码 zip 并解压 |
| FR-DL-02 | 镜像加速 | P0 | 支持配置 GitHub 镜像/加速地址（如 ghproxy 类前缀）与 HTTP 代理；下载失败自动重试并支持断点（zip 分片下载） |
| FR-DL-03 | 下载进度与取消 | P0 | 下载与解压过程显示进度、速度、预估体积；可取消；取消/失败不留半成品目录 |
| FR-DL-04 | 落盘位置 | P0 | 开发态默认 `本项目/tools/`；安装态默认应用数据目录；均允许用户在设置中自定义磁盘路径（如换到 D 盘大空间分区） |
| FR-DL-05 | 手动添加仓库 | P0 | 输入任意 GitHub 仓库地址即可尝试获取；宿主按 FR-CAT-03 规则自动识别类型并生成初始 Manifest，识别失败时以向导引导用户选择类型并填写安装/启动命令 |
| FR-DL-06 | 体积预估提示 | P1 | 获取前展示仓库体积与依赖预估体积（如"约 850MB，含依赖"），避免误装巨型项目 |
| FR-DL-07 | 移除工具 | P0 | 删除工具目录前二次确认；提示该工具的本地用户数据（若有）将一并删除；移除同时停止其运行中进程 |

### 4.3 模块三：工具适配层（"包一层"的核心：Manifest + Runner）

| 编号 | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| FR-ADP-01 | Manifest 规范 | P0 | 定义工具适配清单 JSON 规范，至少包含：`id`、`来源（repo/release）`、`类型（web-node/web-python/web-static/docker/cli/desktop）`、`安装命令`、`启动命令`、`端口或端口获取方式`、`健康检查（URL/TCP/超时）`、`打开地址规则`、`停止方式`、`环境要求（node/python/docker 版本）`、`用户数据目录声明`。规范需有文档与校验器 |
| FR-ADP-02 | web-node Runner | P0 | 使用宿主内置 Node 执行 `npm install` 与启动命令（默认 `npm start`，其次 `npm run dev`）；启动后按健康检查等待就绪 |
| FR-ADP-03 | web-static Runner | P0 | 零依赖直接加载（WebView 打开本地 index.html 或内置静态服务），最轻量的类型 |
| FR-ADP-04 | web-python Runner | P1 | 检测系统 Python/uv → 创建虚拟环境 → 安装依赖 → 启动；Python 缺失时引导安装 |
| FR-ADP-05 | docker Runner | P1 | 检测 Docker → 生成/使用 compose 配置 → `docker compose up -d` → 健康检查 → 打开 |
| FR-ADP-06 | cli Runner | P1 | 安装后在内嵌终端直接可用；支持参数表单模式（Manifest 可声明常用参数生成表单） |
| FR-ADP-07 | desktop Runner | P2 | 下载官方 Release 安装包/绿色包并启动；**明确说明**：桌面程序无法嵌入宿主窗口，将以独立窗口运行，宿主内仅显示状态与"启动/打开目录"入口 |
| FR-ADP-08 | 环境依赖管理 | P0 | 宿主内置 Node 运行时；启动工具前检测 Manifest 声明的环境要求，缺失项给出明确引导（下载 Python/Docker 的官方指引或宿主代装） |
| FR-ADP-09 | Manifest 覆盖 | P1 | 用户可对任意工具的 Manifest 进行可视化编辑（改启动命令、端口等），保存为本地覆盖版本 |
| FR-ADP-10 | 失败诊断 | P1 | 安装/启动失败时展示完整日志，并给出常见原因提示（端口占用、依赖安装失败、Node 版本不符、网络超时），支持"一键重试" |

### 4.4 模块四：生命周期与进程管理

| 编号 | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| FR-LC-01 | 工具状态机 | P0 | `未获取 → 下载中 → 安装中 → 已就绪 → 启动中 → 运行中 → 已停止`，另有 `失败`、`更新可用` 附加态；状态实时反映在卡片上 |
| FR-LC-02 | 启动与就绪判定 | P0 | 点击工具 → 宿主启动进程 → 轮询健康检查（HTTP 200 / TCP 通 / 超时阈值可配，默认 60s）→ 就绪后窗口内打开；超时判定失败并展示日志 |
| FR-LC-03 | 端口池管理 | P0 | 宿主统一分配端口：Manifest 默认端口被占用时自动换端口并通过环境变量（`PORT` 等，Manifest 声明变量名）注入；记录分配表避免互相冲突 |
| FR-LC-04 | 进程守护与退出清理 | P0 | 宿主退出（含崩溃）时确保所有工具子进程树被终止（Windows 下用 Job Object 级联清理）；提供"结束后台进程"手动入口 |
| FR-LC-05 | 停止/重启 | P0 | 使用中的工具可一键停止（杀进程树）与重启；停止后窗口回到工具列表 |
| FR-LC-06 | 后台运行 | P1 | 关闭工具视图时可选"保持后台运行"（记住用户选择），托盘区显示运行中工具 |
| FR-LC-07 | 多工具并行 | P0 | 允许多个工具同时运行（各自端口隔离）；宿主内可切换查看 |
| FR-LC-08 | 版本更新 | P1 | 检测上游更新（新 Release / 新提交）：执行 `git pull`（或重新下载）→ 重装依赖 → 重启工具；支持锁定版本不更新 |
| FR-LC-09 | 用户数据保留 | P1 | Manifest 可声明工具的数据目录（如 SQLite 文件、uploads），更新工具时保留该目录，删除工具时提示是否一并清除 |

### 4.5 模块五：宿主主窗口（唯一窗口的 UI）

| 编号 | 需求 | 优先级 | 说明 |

### 4.9 模块九：分发与部署（自用 + 打包分发双形态）

> 已确认：本项目**既要支持自用（源码运行、工具落在本仓库内），也要能打包成安装包分发给无开发环境的普通用户**。两种形态共用同一套代码与数据模型。

| 编号 | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| FR-DIST-01 | 双形态支持 | P0 | 同一套代码支持两种运行形态。**开发态（自用）**：源码方式运行（如 `npm run dev`），工具仓/数据/运行时直接落在本项目目录（`tools/`、`data/`、`runtimes/`）；**安装态（分发）**：打包为安装包交付他人，上述目录落在系统应用数据目录（Windows：`%APPDATA%\All-Tools\`）。形态由运行时判定（Electron `app.isPackaged`），对业务层透明 |
| FR-DIST-02 | 统一路径解析 | P0 | 宿主内所有磁盘路径（工具仓/数据/运行时/日志/Manifest 本地副本）一律经统一 PathResolver 按形态解析；业务代码禁止硬编码路径。这是双形态零差异的保证，M1 起强制执行 |
| FR-DIST-03 | Manifest 库远程更新 | P1 | 预置 Manifest 随宿主安装包内置；宿主随目录同步（默认每日）从官方源拉取 Manifest 增量与修订，老版本宿主也能获得新适配工具；拉取失败不影响本地已有清单 |
| FR-DIST-04 | 安装包产物 | P1 | 用 electron-builder 产出两类产物：**NSIS 安装包**（开始菜单/桌面快捷方式、卸载器）与**免安装便携版**（Portable zip，解压即用）；代码签名放远期 |
| FR-DIST-05 | 便携版数据策略 | P1 | 便携版默认把工具仓/数据放在程序目录旁的 `Data/` 文件夹，支持整目录拷贝迁移（U 盘/换机）；安装版默认用户数据目录，两者互不干扰 |
| FR-DIST-06 | 首次启动向导 | P1 | 安装态首次启动进入向导：选择数据目录（默认系统盘应用数据目录，可改到空间更大的分区并显示可用空间）→ 可选配置 GitHub Token / 下载镜像 → 可选立即同步工具目录。开发态跳过向导 |
| FR-DIST-07 | 宿主自更新 | P1 | 安装态经 electron-updater 走 GitHub Release 通道（支持镜像）检查并安装更新，更新前提示将停止所有运行中工具并等用户确认；便携版提示下载新包；开发态仅提示"源码有更新，请 git pull" |
| FR-DIST-08 | 无开发环境可用 | P0 | 安装态的目标用户机器**不要求预装任何开发环境**：Node 由宿主内置；Git 缺失时自动走 zip/codeload 下载通道（FR-DL-01）；Python/Docker 仅对应类型工具需要，缺失时给出引导且不影响其它类型工具 |

## 5. 非功能需求

| 编号 | 类别 | 需求 |
| --- | --- | --- |
| NFR-01 | 性能 | 宿主冷启动 ≤3s；工具启动就绪时间受工具自身制约，宿主开销（含健康检查轮询）≤2s 额外；目录搜索 ≤200ms |

## 8. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 开源项目结构千差万别，无法全自动适配所有工具 | 部分工具不能一键用 | 承认边界：官方预置 Manifest 覆盖 Top 热门工具；其余走自动识别 + 向导兜底；Manifest 开放社区共建 |
| 依赖体积巨大（node_modules） | 磁盘快速膨胀 | 获取前体积预估、磁盘看板、pnpm 共享缓存（M3）、按需获取不预装 |
| 工具服务端口冲突、进程残留 | 启动失败/后台占资源 | 端口池统一分配注入、Job Object 级联清理、孤儿进程回收 |
| 运行第三方代码的安全风险 | 恶意代码损害本机 | 命令透明可审计、来源仅官方仓库/Release、WebView 权限隔离、工具进程以受限权限运行（远期沙箱） |
| GitHub 访问受限 | 下载/更新失败 | 镜像与代理配置、zip 通道兜底、Release 缓存 |
| 上游工具升级破坏适配（脚本更名、构建变化） | 工具突然起不来 | Manifest 支持版本锁定；更新失败自动回滚到旧版本目录 |
| Electron 体积/内存偏大 | 轻量用户嫌弃 | 接受换取内置 Node 的免环境优势；远期可评估 Tauri + sidecar 方案 |

## 9. MVP 验收用例

1. 首次启动完成引导（Token 可选）→ 工具目录呈现 ≥10 个预置适配工具，覆盖 ≥3 个分类；
2. 点击获取一个 web-node 工具：可见下载→安装进度与日志 → 卡片变"已就绪"；
3. 点击已就绪工具：宿主启动服务 → 健康检查通过 → **窗口内打开该工具界面** → 完成一次真实操作（如保存一个文件）；
4. 点击"停止"：进程树被清理（任务管理器无残留）；宿主直接退出同样无残留；
5. 获取一个 web-static 工具：无需任何依赖，秒级就绪并在窗口内打开；
6. 手动粘贴一个未适配的仓库地址：能进入向导完成类型选择与启动命令填写并成功运行；
7. 断网重启宿主：已获取工具全部可正常启动使用；工具目录可离线浏览。
